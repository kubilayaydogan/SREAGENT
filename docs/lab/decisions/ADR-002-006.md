# ADR-002 … ADR-006

## ADR-002 JPA yerine JdbcClient + TransactionTemplate
**Karar:** Tüm SQL elle yazıldı; transaction sınırları `TransactionTemplate` ile açık.
**Neden:** Kilit sırası, hangi satırın hangi kipte kilitlendiği ve SQL yorumu (op/rid/exp) sunumda gösterilebilir olmalı.
ORM'in flush sırası ve ek SELECT'leri lock analizini bulanıklaştırır.
**Bedel:** Daha fazla kod; şema değişikliğinde SQL güncellenir.

## ADR-003 Tek database, şema başına sahiplik, servis başına rol
**Karar:** `airlab` DB; `flightops/reservation/checkin/baggage` şemaları; her servis ayrı login rolü ve ayrı
`ApplicationName`; çapraz okuma GRANT SELECT ile, ortak satıra yazma kolon bazlı GRANT UPDATE ile.
**Neden:** Talimat aynı instance+database istiyor; `pg_stat_statements` application_name taşımadığı için rol = servis
eşlemesi zorunlu. Kolon GRANT'ları "kim ortak satırın neyini değiştirir" sorusunu belgeler ve test edilir.

## ADR-004 chaos-controller yalnız HTTP; lab uçları uygulamada
**Karar:** chaos'un DB sürücüsü yok. Kilit/bağlantı tutma gerektiren senaryolar uygulamaların `/lab/**` uçlarında,
**gerçek iş yolu** üzerinde (ör. rezervasyon oluşturup envanter kilidi tutulurken sınırlı `pg_sleep`).
**Neden:** Gerçekçi bekleme zinciri (uygulama → JDBC → aynı satır) ve servis/rol eşlemesi; keyfi SQL yüzeyi yok.
**Güvenlik:** profil + token + CIDR + süre/eşzamanlılık sınırı + cleanup.

## ADR-005 Küçük salt-okur collector
**Karar:** Python collector 5 sn'de bir `pg_blocking_pids` zinciri, rol×app oturumları, kapasite, rol bazlı
pg_stat_statements deltası üretir ve Dynatrace'e metrik+log olarak yollar.
**Neden:** PostgreSQL extension varsayılan 1 dk örnekler ve rol/app boyutu sunmaz; 2–4 sn'lik kilit zincirleri ve
kaynak/etkilenen servis eşlemesi bu boşluğu doldurur. Agent değildir: karar vermez, sorgu sonlandırmaz.
**Bedel:** Ek ingest tüketimi (ölçülmeli), tek nokta; `collector.up` ile görünür.

## ADR-006 Tek pool doluluğu ≠ global DB bağlantı tükenmesi
**Karar:** Ana Hikari havuzu (8) ve tembel açılan `<servis>-lab-pressure` havuzu (≤22) ayrıdır; rol limiti 40.
**Neden:** E3 yalnız bir servisin kendi havuzunu doldurur (DB bağlantı sayısı değişmez); E4 instance'ın normal
slotlarını doldurur. Farklı paydalar: `hikaricp.connections.active/max` vs `connections.used/normal_slots`.
Rol limiti global limitten önce dolmaz, böylece iki durum karışmaz.
**Gözlem (yerel):** Ana havuzlar mevcut bağlantılarını koruduğu için E4 sırasında arka plan trafiği hata vermedi;
global baskı yeni bağlantı isteyen havuzlarda acquire gecikmesi olarak göründü.
